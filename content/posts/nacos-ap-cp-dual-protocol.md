「注册中心到底该选 AP 还是 CP？」这是个吵了很多年的问题。选 AP（可用性优先），注册中心脑裂时每个节点都能响应，但可能返回过期的地址；选 CP（一致性优先），地址保证准确，但网络分区时可能整个写不可用。Eureka 选了 AP，ZooKeeper 选了 CP，各挨各的骂。

Nacos 的回答是：**都要，而且混跑在同一个集群里**。它用「临时实例 + Distro 协议」扛微服务的高可用，用「持久实例 + JRaft 协议」保证数据库这类基础组件地址的强一致。这篇想讲清这两套协议为什么能并存、各自付出什么代价，以及一个容易被忽略的细节——「30 秒删除」其实只对临时实例生效。

## 两种实例，是理解 Nacos 的钥匙

Nacos 把注册进来的实例分成两类，这是它整个设计的根：

| 维度 | 临时实例（默认） | 持久实例 |
| :--- | :--- | :--- |
| 一致性协议 | Distro（AP） | JRaft（CP） |
| 健康检查 | 客户端上报心跳（5s 一次） | 服务端主动探测（TCP/HTTP） |
| 剔除机制 | 超时 15s 不健康、30s 删除 | 标记不健康但**不删除** |
| 存储 | 内存注册表 | 持久化到数据库 |
| 适用 | 普通微服务（推荐默认） | 数据库、Redis、K8s 场景 |

为什么这么分？因为这两类实例对「地址准确性」的要求完全不同：**微服务实例挂了就挂了，消费者换个实例就行，宁可返回一个可能过期的地址也不能拒绝服务（所以走 AP）；而数据库这类基础组件，地址错了就是致命的，必须强一致（所以走 CP）**。

这是 Nacos 区别于 Eureka（纯 AP）和 ZooKeeper（纯 CP）的根本点：它不是二选一，而是按实例类型「混跑」两套协议。

## AP 侧：Distro 的五大机制

临时实例走 Distro——Nacos 社区自研的 AP 协议，它集成了 Gossip 和 Eureka 数据同步算法的长处，又针对 Gossip「随机选节点发送会重复推送」的问题做了优化，引入「权威 Server（责任节点）」来降低消息冗余。

它的五大机制是：

- **平等机制**：每个节点都能处理写请求，没有主从。
- **路由转发**：写请求按 IP+port 算出责任节点，不属于自己的转发过去。
- **异步复制**：责任节点写本地内存后，异步同步给其他节点。
- **本地读**：每台机器都持有全量数据，读请求直接本地响应——这是 AP「可用性」的来源。
- **数据校验**：节点间定期交换元信息（不是全量数据），发现不一致就触发全量拉取补齐。

核心源码链路里有个值得注意的工程细节：写请求落本地内存后，Distro 会**延迟 1 秒**再把数据同步给其他节点，而不是立即同步：

```java
distroProtocol.sync(new DistroKey(key, KeyBuilder.INSTANCE_LIST_KEY_PREFIX),
                    DataOperation.CHANGE,
                    DistroConfig.getInstance().getSyncDelayMillis());   // 默认 1000ms
```

为什么要延迟 1 秒？**把短时间内的高频写操作合并成一次同步**，显著降低节点间流量。这是 Distro 相比朴素 Gossip 的工程优化。但它的代价也很明确：这 1 秒就是一个「不一致窗口」——一个实例刚注册，其他节点可能要等 1 秒才看得到。

## 那个容易被忽略的细节：30 秒删除只对临时实例生效

临时实例的健康检查是「客户端上报心跳」，5 秒一次。服务端判定逻辑是一条清晰的阈值链：

- 超过 **15s** 没收到心跳 → 标记 `unhealthy`，不再返回给消费者；
- 超过 **30s** 没收到心跳 → 直接从注册表**删除实例**。

注意删除阈值恰好是「2 × 不健康阈值」，而且——**30 秒删除只适用于临时实例**。持久实例心跳超时只会被标记不健康，不会被删除，因为它的存活依据是服务端探活，不是客户端心跳。

这个细节为什么重要？因为很多「实例被删了」的线上问题，根因就是这里：一个临时实例因为 GC 停顿、网络抖动，30 秒没发心跳，就被 Nacos 删了——而消费者还在用本地缓存调用它。理解「临时实例靠心跳续命、30 秒是死线」，你才能在排查时一眼定位到「为什么服务突然不在列表里了」。

## CP 侧：为什么选 JRaft 而不是 ZAB

持久实例和配置中心数据走 CP，Nacos 集成了蚂蚁的 SOFAJRaft 实现。为什么不用 ZooKeeper 的 ZAB？官方的理由很直接：**ZAB 和 ZooKeeper 强绑定，不能独立使用；而 JRaft 支持多 RaftGroup**，为 Nacos 后续的数据分片能力留了空间。

JRaft 的核心机制是标准的 Raft：Leader 选举（任期 + 多数派投票）、日志复制（写请求 → Leader → 多数派确认 → 提交）、安全的成员变更。这套东西保证了持久实例地址的强一致，代价是写要过 Leader、要多数派确认，延迟和可用性都不如 AP 侧。

把几类组件放一起对比，Nacos 的定位就清楚了：

| 组件 | CAP | 特点 |
| :--- | :--- | :--- |
| Nacos | AP/CP 可切换 | 注册 + 配置二合一，模型最灵活 |
| Eureka | AP | 简单，已停止维护 |
| ZooKeeper | CP | 强一致，作注册中心过重 |
| Consul / etcd | CP | 多数据中心 / K8s 原生 |

## 代价的另一面：灵活是优点，也是复杂度

Nacos 的「AP/CP 可切换」是优点，但它也把选择权交还给了你——**选错了实例类型，就等于选错了协议**。

一个真实的翻车场景：你把 Redis、MySQL 这类基础组件注册成了默认的**临时实例**。结果网络一抖、心跳超时 30 秒，Nacos 就把这个「数据库地址」从注册表删了，下游消费者拿到的是过期缓存，甚至直接查不到。基础组件地址的正确性要求高，本该走**持久实例 + 服务端探活**，你却让它用「客户端心跳续命」的临时实例模型，这就是典型的「灵活带来的误配」。

所以那句实践结论很硬：**普通微服务用临时实例（默认），数据库/Redis/K8s 这类基础组件显式切持久实例**。`ephemeral: false` 这一个配置，背后是 AP 到 CP 的完整切换。

## 收口

「注册中心选 AP 还是 CP」在 Nacos 这里不再是二选一：它用临时实例扛微服务的可用性，用持久实例保基础组件的准确性，两套协议（Distro + JRaft）在同一个集群里并存。这不是「取巧」，而是看清了「不同的服务，对地址准确性有不同要求」这个本质。

但灵活是有代价的：1 秒的 Distro 同步窗口、30 秒的心跳死线、以及「选错实例类型」带来的协议错配，都等着你去理解、去规避。Nacos 的深度，不在于它「支持 AP 和 CP」，而在于它让你想清楚——**你手上这个服务，到底该为可用性让步，还是为一致性让步**。

延伸一个问题：配置中心的动态刷新靠的是「长轮询 + MD5 比对」，客户端挂一个 30 秒的长轮询去问「配置变了没」。那么 Nacos 2.x 为什么要把这套东西从 HTTP 短轮询换成 gRPC 长连接？长连接又带来了哪些 1.x 没有的新问题？
