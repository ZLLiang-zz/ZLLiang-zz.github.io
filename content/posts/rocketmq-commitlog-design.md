如果你写过 RocketMQ，大概率听过这个说法：RocketMQ 里所有 Topic 的消息，都顺序追加写进同一个叫 CommitLog 的文件。第一次听到时很容易懵——一个集群里几百个业务 Topic，消息全混在一个文件里，那消费者拉消息的时候，凭什么能 O(1) 地找到属于自己的那几条？这不反而更慢吗？

这正是 RocketMQ 最有辨识度的架构决策，也是它和 Kafka 最本质的分野。这篇想讲清楚两件事：这个「混写」设计解决了什么问题、又付出了什么代价，以及它为什么在「多业务共享一个集群」的公司内部场景里是更优解，而在「少数超大吞吐 Pipeline」场景里不如 Kafka。

## 三个文件：消息到底存在哪

先建立心智模型。RocketMQ 的存储由三个文件组成，分工明确：

| 文件 | 作用 | 关键点 |
| :--- | :--- | :--- |
| **CommitLog** | 消息物理存储，所有 Topic 混写 | 顺序追加，单文件默认 1GB |
| **ConsumeQueue** | 逻辑队列索引（按 Topic/Queue 维度） | 每条 20 字节定长 |
| **IndexFile** | 消息索引，支持按 Key/时间查询 | 哈希表结构 |

ConsumeQueue 的每条记录只有 20 字节：`CommitLog Offset(8B) + Size(4B) + Tag HashCode(8B)`。因为定长，所以「第 N 条消息」的位置可以直接算出来，定位是 O(1)。

数据流转路径是：Producer 发消息 → Broker 顺序写进 CommitLog → 刷盘 + 主从复制 → `ReputMessageService` 异步分发、构建 ConsumeQueue 和 IndexFile → Consumer 拉取时先查 ConsumeQueue 拿到 CommitLog 偏移量，再通过 mmap 从 CommitLog 读消息体。

注意这条链路的两个关键点：**写入是顺序的，索引是异步构建的**。这两点决定了它的一切优点和代价。

## 为什么敢「混写」：顺序写是磁盘的命门

把消息混写进同一个文件，是为了一个朴素但决定性的事实：**磁盘的随机写比顺序写慢一个数量级**。

机械硬盘上，随机写要做寻道和旋转延迟，单次可能几十毫秒；顺序追加写则几乎没有寻道开销，写的是连续的扇区。即使到了 SSD，随机写的代价降低了，但顺序写依然在吞吐和写放大上占优。

如果像 Kafka 那样每个 Partition 各维护一个日志文件，那么当 Topic/分区数量很多时，写盘动作就会散落在很多个文件上，退化成随机写，页缓存竞争也会加剧。RocketMQ 把所有消息都往一个 CommitLog 里追加，**无论业务 Topic 有多少个，磁盘始终是纯顺序写**。这就是「写路径极致简化」的全部含义。

代价也很清楚：读路径多了一次间接寻址。消费者不能直接从「自己的分区文件」读，得先查 ConsumeQueue 拿偏移量，再跳回 CommitLog 读消息体。RocketMQ 用 20 字节定长条目把这一次间接寻址压到了极低的开销——这正是一个「用读换写」的典型权衡。

一句话总结这个设计：**它适合「多业务共享一个集群」的公司内部场景，Kafka 更适合「少数超大吞吐 Pipeline」**。这也是为什么你会看到很多公司内部用 RocketMQ、而大数据管道用 Kafka 的格局。

## mmap：读写的真正载体

RocketMQ 的读写都围绕 `MappedByteBuffer`（mmap）展开，但这里有个容易被夸大的点：**它并不是严格意义上的 sendfile 零拷贝**。

- **写路径**：消息写入 mmap 映射的页缓存，由 OS 异步刷盘。开启 `transientStorePoolEnable=true` 时，先写堆外 DirectBuffer 再 commit 到 FileChannel，实现读写缓冲隔离，避免写抖动影响读——代价是额外内存和略增的 commit 延迟。
- **读路径**：消费者直接读 mmap 页缓存，热数据大概率还在 Page Cache 里，避免了磁盘 IO。但从 Broker 到网卡，仍有一次内核态到用户态的拷贝。

而 Kafka 的 sendfile 可以让数据从磁盘直接进网卡、根本不进用户态。**这是 Kafka 极限吞吐普遍高于 RocketMQ 的原因之一**——又是「混写换顺序写」之外，RocketMQ 在吞吐上的一个真实短板。

为了压榨 mmap 的性能，RocketMQ 还做了文件预热和锁页：新建 MappedFile 时预写 0 遍历整个文件、提前触发缺页中断，再用 `mlock` 锁页防止被换出、`madvise(MADV_WILLNEED)` 提示预读。一句话概括这个设计意图：「把 mmap 首次访问的缺页抖动，从读路径消灭在写路径」。

## 代价一：刷盘，快与不丢之间的拉锯

消息写进页缓存，还只是写进了内存。什么时候真正落到磁盘，决定了「快」和「不丢」的边界。

| 刷盘方式 | 语义 | 风险 |
| :--- | :--- | :--- |
| 异步刷盘（默认） | 写页缓存即返回，后台批量刷 | Broker 宕机丢页缓存里没刷的数据 |
| 同步刷盘 | 落盘后才回 ACK | 吞吐下降 30%~50% |

同步刷盘里有个反直觉的细节：它**不是每条消息一次 `fsync`**——那样 IOPS 直接被打死。RocketMQ 用 GroupCommit 把并发写入合并成一次刷盘：多个线程的刷盘请求进队列，刷盘线程一次 `fsync` 把所有已写数据落盘，再批量唤醒所有等待者。

所以「同步刷盘 TPS 还能到几万」的真相是「一批一次 fsync」；而代价是**单条消息的 RT 至少是一个刷盘周期**（最坏 10ms 级）。并发越高，单次 fsync 摊到每条消息的成本越低；但延迟的下限始终在。

## 代价二：复制，异步 vs 强一致的边界

刷盘解决了单机的持久化，但单机宕机依然会丢。主从复制才是高可用的关键，而它默认同样是**异步**的——Master 写完就返回，命令异步同步给 Slave。

这带来一个一致性缺口：Master 写成功、异步复制还没完成就宕机，Slave 数据不全，却可能被选为新 Master，于是丢消息。`SYNC_MASTER` 能缓解（等 Slave 落盘再回 ACK），但它是「主从 + 半同步」，没有任期、没有投票、没有日志一致性检查，**本质仍不是共识协议**。

要真正强一致，RocketMQ 提供 DLedger：把 CommitLog 的写入改成 Raft 日志复制——写入发 Leader，Leader 并行发给 Follower，过半数确认才 committed，Leader 挂掉后只有日志最新的节点能当选。代价是吞吐略低（日志双写 + 投票开销）、需要 3/5 节点奇数部署。

这条拉锯的结论很实用：金融级「不允许丢」用 DLedger（或 5.x 的 Controller 模式），一般业务 `SYNC_MASTER` + 3 副本就够。**「不丢」与「不重」不可同时免费获得**——要「不丢」就必须允许重试重投，所以是「至少一次」，要「不重」就得在消费端做幂等，用存储换。

## 收口

回到开头：RocketMQ 把所有消息混写进一个 CommitLog，本质是用「读路径多一次间接寻址」换「写路径永远顺序追加」。这个交换在公司内部多业务共享集群的场景里是划算的，因为 Topic 再多、写盘也永远是顺序的；但它也注定了两件事——读要绕一道 ConsumeQueue，极限吞吐拼不过 sendfile 零拷贝的 Kafka。

理解了 CommitLog，你再看 RocketMQ 的其他设计就都是同一条思路的延伸：GroupCommit 是「用延迟换 IOPS」，DLedger 是「用吞吐换强一致」。没有一个设计是免费的，选型的本质是判断你的业务该在哪一端让步。

延伸一个问题：如果一条延时消息在投递前被消费者反复重试，它到底被「重写」了几次、重写发生在哪一层？这个细节能帮你理解延时消息和普通消息在存储层完全不同的生命周期。
