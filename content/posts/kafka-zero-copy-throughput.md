Kafka 有个看起来「反常识」的配置：Broker 的 JVM 堆通常只给 6~8GB，却能在单机上扛住几十万条消息每秒的吞吐。要知道，很多中间件一提到大流量就要堆内存、加线程，凭什么 Kafka 用小堆就能撑住？

答案藏在它的存储和传输设计里：**消息既不进 JVM 堆，也不进用户态**。这篇想讲清 Kafka 高吞吐的两根支柱——「分段 + 稀疏索引」的三段式查找，和「sendfile 零拷贝」省掉的那两次拷贝——更重要的是，这两根支柱各自在什么条件下会崩塌。理解了失效条件，你才算是真正理解了它，而不是只会背「零拷贝快」。

## 一个 Partition 在磁盘上长什么样

Kafka 的一个 Partition 在磁盘上就是一个目录，里面是一串分段文件：

```text
order-0/
├── 00000000000000000000.log        # 消息本体，默认 1GB 切一个
├── 00000000000000000000.index      # offset → 物理位置（稀疏）
├── 00000000000000000000.timeindex  # 时间戳 → offset
├── 00000000000000001234.log        # 下一个 Segment，文件名 = baseOffset
└── leader-epoch-checkpoint         # Leader Epoch 历史
```

消费者给定一个 offset，Broker 要找到这条消息，走的是「三段式查找」：

1. 用 offset 在 `.index` 里做二分，找到**不大于目标 offset 的最近一条索引项**。
2. 拿到物理 position，到 `.log` 里**顺序扫描**（通常只扫几 KB）定位到目标消息。
3. 返回 `(offset, size, 数据)`。

这里的关键是「稀疏索引」：不是每条消息都建索引，而是默认每 4KB 记一条。为什么这么设计？全量索引会让索引文件和数据文件一样大，写放大翻倍；稀疏索引把索引控制在数据的千分之一量级，代价是定位后要顺序扫几 KB——**磁盘顺序读几 KB 和读一次索引几乎同价**，所以这是「用一点顺序扫描换巨大空间节省」。三段式查找，就是「Kafka 为什么快」的核心答案之一。

Segment 默认切 1GB，同样是个权衡：太小则文件数爆炸（每个文件都要开 fd、建索引），太大则删除滚动粒度粗、索引文件过大拖慢二分。

## 零拷贝：省掉的到底是哪两次拷贝

传统 `read + write` 把磁盘上的数据发到网卡，要经过四次拷贝：

```text
磁盘 → 内核页缓存（DMA 拷贝）
     → 用户态缓冲区（CPU 拷贝）
     → 内核 socket 缓冲区（CPU 拷贝）
     → 网卡（DMA 拷贝）
```

四次拷贝、四次用户态/内核态切换。而 `sendfile`（Java 里是 `FileChannel.transferTo`）把它砍成两次：

```text
磁盘 → 内核页缓存（DMA）
     → 内核 socket 缓冲区（仅传描述符，不拷贝数据）
     → 网卡（DMA）
```

两次拷贝、两次切换，**数据完全不进用户态**。Kafka 的实际路径是：Consumer 发 Fetch 请求 → Broker 从 Segment 定位到 `(position, size)` → 直接 `transferTo` 到 socket。消息不经过 JVM 堆，所以不受 GC 影响、也不占堆内存——这正是 Kafka 能用小堆撑大流量的根本原因。

## 零拷贝什么时候失效

「零拷贝快」是常识，「零拷贝会失效」才是深度。两个真实条件：

**第一，开启 TLS/SSL 后零拷贝失效。** 加密必须在内核缓冲区之外做，数据不得不进用户态。所以 TLS 集群的吞吐会明显下降，常见 20%~40%。这不是 Kafka 的实现问题，而是加密的固有成本——你想清楚这一点，就不会在「既要端到端加密又要极限吞吐」时感到困惑。

**第二，消息格式要被 Broker 改写时也无法零拷贝。** 老版本 `message.format.version` 转换会触发解压重编；只有 `compression.type=producer`（默认，Broker 原样转发）时才能保持零拷贝。一旦 Broker 端配置了重新压缩，路径就退化成用户态。

这两条背后是同一个判断逻辑：**零拷贝的前提是「数据从磁盘到网卡一路原样透传」。** 只要中途要「碰」数据（加密、转格式、重压缩），就得把它捞进用户态，零拷贝就破了。

## 消费端的一致性：HW 与 Leader Epoch

高吞吐之外，Kafka 的副本同步还有一套容易踩坑的一致性机制。三个量要先分清：

- **LEO**：每个副本自己的写入进度。
- **HW**：`min(ISR 中所有副本的 LEO)`，消费者只能读到 HW 之前——保证「读到的消息不会因 Leader 切换而消失」。
- **ISR**：跟得上 Leader 的副本集合，按 `replica.lag.time.max.ms`（默认 30s）内是否追上过 Leader 来判定，**不是按条数差**。

早期 Kafka 把「哪些消息对消费者可见」和「故障恢复时该截断到哪里」这两件事都压在 HW 上，结果出了经典的截断不一致 bug：HW 是异步传播的，不同副本看到的 HW 不同，恢复时可能截多或截少。

Leader Epoch（KIP-101）的解法是把这个职责拆开：每次 Leader 变更 epoch +1，每个副本记录 `(epoch, startOffset)`；Follower 恢复时先问新 Leader「你在这个 epoch 的起始 offset 是多少」，据此**精确决定截断点**，而不是拿自己的 HW 猜。一句话总结：**HW 管「可见性」，Leader Epoch 管「截断点」**——把两件事压在同一个量上，才会出问题。

## 代价：Rebalance 的 Stop-The-World

Kafka 消费端最疼的地方是 Rebalance。传统 Eager 协议分三步：所有成员向 Coordinator 报到选出 Leader Consumer → Leader 算分配方案分发给所有人 → 心跳维持。**第 ① 步一开始，所有消费者就停止消费**，直到分配完成——几十个消费者、上千分区的组，一次 Rebalance 能停几十秒。

这也是为什么工程上要花力气减少 Rebalance：静态成员 `group.instance.id` 让 K8s 滚动发布的重启不触发 Rebalance；控制 `max.poll.interval.ms`（默认 5min，单批处理超过它就会被踢出组）；优雅停机先 `close()` 再退出。3.7+ 的 KIP-848 新协议把「客户端算分配」改成「服务端算分配」，Rebalance 时间从秒级降到毫秒级——这是目前 Kafka 消费端最大的一次架构变化。

还有一个常见的「灵异现象」来源：位点不是存在 ZooKeeper，而是存在内部 Topic `__consumer_offsets` 里，默认保留 7 天。**消费者组连续 7 天不活跃，位点会被清除**——「服务停了一周再上线，发现消息没消费」，就是这个原因，而不是 bug。

## 收口

Kafka 的高吞吐不是靠堆内存堆出来的，而是「分段稀疏索引 + sendfile 零拷贝」把读路径压缩到了极致，让消息一路不进用户态。但这两根支柱都有明确的失效条件：数据一旦需要被「碰」（加密、转格式），零拷贝就破了；索引一旦做全量，写放大就回来了。

理解 Kafka 的正确姿势，是把「快」还原成具体的机制和边界，而不是一句「零拷贝 + 顺序写」。这样你才能在「开 TLS 吞吐下降」「停一周消息丢了」「消费逻辑慢引发反复 Rebalance」这些现象出现时，一眼看到根因。

延伸一个问题：如果一个长事务卡住了 LSO，后面所有开启 `read_committed` 的消费者都会读不到新消息——这个「一个长事务拖垮所有人」的边界，你打算用什么手段兜底？
