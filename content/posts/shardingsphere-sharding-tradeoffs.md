单表撑到几千万行、单库扛到几百 QPS，你就该考虑拆了。但很多人在拆之前只看到了「拆完就不堵了」，没看到拆完当天会多出来的东西：你之前 `JOIN` 一下就能查的关联数据，现在散在十几个分片里；你之前 `ORDER BY ... LIMIT` 就能翻页，现在中间件要把每个分片的前 N 条都捞出来归并；你之前一个事务能包住的写操作，现在横跨多个库。

分库分表解决的是「容量和并发」的瓶颈，代价是「查询和事务的复杂度」整体上移。这篇想讲清楚这个代价具体是什么、中间件（以 ShardingSphere 为例）在中间帮你扛了多少、又有哪些是它扛不了、必须你自己扛的。

## 中间件做了什么：内核五阶段

分片中间件最容易被问住的不是「支不支持分片」，而是「一条 SQL 进去，中间到底做了什么」。ShardingSphere 5.x 的链路拆成五阶段：

```text
逻辑 SQL
  → ① 解析（Parse）     文本 → SQLStatement（AST）
  → ② 路由（Route）     分片规则 → RouteContext（目标库表集合）
  → ③ 改写（Rewrite）   逻辑 SQL → 可执行的物理 SQL 列表
  → ④ 执行（Execute）   多线程下发
  → ⑤ 归并（Merge）     多结果集 → 单一结果集
```

其中**路由**这一阶段决定了性能上限，它从 `WHERE` 里提取分片键、代入分片算法算出目标库表。按命中情况分五类：

| 路由类型 | 触发条件 | 下发分片数 |
| :--- | :--- | :--- |
| 标准路由 | `=` / `IN` 命中分片键 | 1~N |
| 范围路由 | `BETWEEN` / `>` / `<` 命中分片键 | 连续若干 |
| 广播路由 | 不带分片键、DDL、全局表 | **所有分片** |
| 单播路由 | 只涉及一个分片 | 1 |
| 阻断路由 | 不支持的 SQL | 0（报错） |

看到「广播」和「阻断」这两行，就理解了分库分表最重要的一个原则：**`UPDATE`/`DELETE` 不带分片键，多数版本会直接阻断，而不是广播**。为什么？因为广播更新无法保证原子性——`UPDATE t_order SET status=1 WHERE status=0` 打到所有分片，影响行数是各片之和，但中途失败会留下「部分片已更新」的状态。中间件选择拒绝，逼你把分片键补上，这是保护，不是缺陷。

## 代价一：跨库分页为什么这么贵

这是分库分表下最典型的性能陷阱。`ORDER BY create_time LIMIT 1000000, 10` 在单库上代价已经不小，在分片下直接爆炸：中间件**无法提前知道全局第 100 万条落在哪个分片**，只能让每个分片都返回前 1000010 条，再在内存里排序、丢弃前 100 万条。

实际传输量是「分片数 × (offset + limit)」。这就是「跨库深分页为什么贵」的源码级答案。

解法按优先级排：**第一，禁止深分页**，改成游标分页（`WHERE id < last_id ORDER BY id DESC LIMIT 10`）；第二，让分片键参与排序，减少归并基数；第三，二次查询法（先只查 id 归并定位，再按 id 回查明细）；第四，复杂检索交给 ES 这类异构索引。核心原则是：**别让中间件替你做全量排序，它做不起**。

## 代价二：跨库 join 与跨库事务

跨库 join 的解法是一个「能规避就规避」的阶梯：小字典表做成**全局表**每个分片冗余一份；有明确父子关系的做成**绑定表**按同一分片键分片；常查字段直接**冗余**到主表；实在要 join 的，中间件分别查询后在内存归并，但只适合数据量小、分页明确的场景。

跨库事务更难。单库事务 ACID 是白送的，跨库之后这张白送的牌没了，你面对的是五种方案：

| 方案 | 一致性 | 适用 |
| :--- | :--- | :--- |
| 弱 XA（MyCat） | 弱 | 不推荐核心链路 |
| XA（ShardingSphere/JTA） | 强（ACID） | 一致性要求高、并发不高 |
| BASE / Saga | 最终一致 | 高并发核心业务主流 |
| 本地消息表 / MQ | 最终一致 | 最常用，落地可靠 |
| Seata AT | 最终/准强 | 微服务场景 |

结论是一句很实在的话：**能规避就规避**——按分片键把关联数据放同库，让跨库事务退化成本地事务；规避不了，就走「本地消息表 + 对账补偿」。

## 代价三：不带分片键，你的 SQL 会走向四种结局

「分片键选错了怎么办」，答案藏在「不带分片键的 SQL 会走到哪」里。四种结局，性能差三个数量级：单播和标准路由是「正常」，广播是「返回正确但慢、分片数倍放大」，阻断是「直接抛异常」。

判断一条 SQL 会不会广播，看三步：`WHERE` 里有没有分片键且是 `=`/`IN`/`BETWEEN`；分片键有没有被函数包裹（`WHERE DATE(create_time)=...` 会让路由失效）；多表关联时是不是绑定表。这三步走完，你基本能预判任何一条 SQL 在分片下的命运。

优化的优先级同样清晰：**补分片键**（从上游把 `user_id` 传下来）是最优解，多数场景做得到；做不到再考虑异构索引表（按另一维度冗余一份，写放大 2 倍）、同步到 ES、或 Hint 强制路由。

## 最后一个代价：扩容

很多人没意识到，**分片算法的选择，本质是对未来扩容成本的选择**。取模分片 `N → 2N` 时，几乎所有数据的目标分片都会变，必须全量重分布；一致性哈希的迁移量约是 1/N。所以「一开始用取模省事」，会在你第一次扩容时连本带利还回来。

平滑扩容的标准做法是**双写迁移**：新老库双写 → 历史数据迁移 → 校验 → 切换 → 回滚观察，四阶段状态机配合幂等设计。这是另一个大话题，但要点只有一个：**扩容不是「加几台机器」那么简单，它需要一条完整的迁移流水线**。

## 收口

分库分表从来不是「拆完就结束了」，而是「拆完才开始」。中间件帮你扛住了路由、改写、归并这些机械劳动，但跨库 join、跨库分页、跨库事务、不带分片键、扩容迁移——这些它扛不了的部分，才是你真正的成本。

所以判断「要不要拆」的标准，不是「表是不是太大了」，而是「你愿不愿意、有没有能力支付拆完之后的那笔复杂度账单」。拆之前，先把分片键想清楚：它决定了你未来每一条 SQL 是「标准路由」还是「广播」。

延伸一个问题：如果你按 `user_id` 分片，但运营后台要按「订单创建时间」跨用户查询，你会怎么做——是加一张按时间分片的异构索引表，还是把数据同步到 ES？这两个方案的写放大和一致性代价差在哪？
