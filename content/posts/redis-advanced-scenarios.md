如果问「Redis 最常被用来干什么」，很多人会脱口而出「缓存」。但真正让 Redis 无处不在的，是它顺手扛下的一堆「高级场景」：缓存、分布式锁、限流、排行榜、延迟队列。这些场景有一个共同点——**原理都不复杂，但正确用法讲究，坑全藏在细节里**：缓存穿透和击穿是两个不同的问题，分布式锁在主从切换时会「双持」，限流在整点会出现突刺。

这篇不追求穷举，只把每个场景「怎么用对」和「哪里会踩坑」讲清楚。读完你应该能区分穿透/击穿/雪崩、写出一把不会误删别人的锁、选对限流算法，以及最重要的一件事：什么时候根本不该用 Redis 锁。

## 缓存三大问题：穿透、击穿、雪崩是三个不同的病

这仨名字像、病因完全不同，混着答是新手最常见的错误。

| 问题 | 现象 | 病根 | 解法 |
| :--- | :--- | :--- | :--- |
| **穿透** | 查不存在的数据，每次都打到 DB | 缓存和 DB 都没有，缓存形同虚设 | 布隆过滤器；缓存空值并设短 TTL |
| **击穿** | 某个热点 key 过期，瞬间大量请求并发重建 | 热点 key 失效那一刻的并发 | 互斥锁重建；逻辑过期；永不过期 |
| **雪崩** | 大量 key 同时过期，或 Redis 整体宕机 | 过期时间集中 / 单点失效 | TTL 随机打散；高可用；限流降级 |

区分的关键在「查的是不是存在的 key」：穿透是查一个**根本不存在**的东西（比如恶意遍历 UUID），击穿是查一个**存在但刚好过期**的热点。

**穿透**用布隆过滤器或缓存空值。布隆过滤器的特性是「**存在可能误判、不存在一定不漏**」——所以它能把绝大多数不存在的 key 挡在缓存之外。误判率由位数组大小、哈希函数个数、元素数共同决定，1% 误判率约需每元素 9.6 bit。它不支持删除（要用 Counting Bloom Filter 或布谷鸟过滤器）。缓存空值则是给「查不到」的结果也缓存一条、设个短 TTL，代价是要防着被恶意 key 撑爆，所以得配上游参数校验。

**击穿**的核心是「只让一个请求去重建」。经典写法是互斥锁 + 双重检查：

```java
public String getWithLock(String key) {
    String value = redis.get(key);
    if (value != null) return value;

    String lockKey = "lock:" + key;
    Boolean locked = redis.setIfAbsent(lockKey, "1", Duration.ofSeconds(10));
    if (Boolean.TRUE.equals(locked)) {
        try {
            value = redis.get(key);   // 双重检查：可能已被前一个线程重建
            if (value == null) {
                value = loadFromDB(key);
                redis.set(key, value, Duration.ofMinutes(30));
            }
            return value;
        } finally {
            redis.delete(lockKey);
        }
    } else {
        Thread.sleep(50);
        return getWithLock(key);   // 自旋等待或返回旧值
    }
}
```

对比方案是「逻辑过期」：value 里内嵌过期时间字段、物理 TTL 永不设置，发现逻辑过期后异步重建、当前请求直接返回旧值——**牺牲一致性换可用性**，适合热点且容忍短暂旧值的场景。

**雪崩**最朴素的解法是 TTL 随机打散：基础 30 分钟，随机偏移 ±5 分钟，让过期时间错开。再往上就是高可用 + 限流降级兜底。

## 缓存一致性：为什么是「先更 DB，再删缓存」

缓存和 DB 的一致性，正确的默认姿势是 **Cache Aside（旁路缓存）**，而且有两个「为什么」很多人说不清：

**第一，为什么「删缓存」而不是「更新缓存」？** 因为并发写时更新缓存会乱序覆盖——后写的旧值可能覆盖先写的新值；而且缓存值如果需要多表计算，更新成本高。删除是幂等的，也是懒加载的。

**第二，为什么「先更 DB、后删缓存」而不是「先删缓存、后更 DB」？** 先删后更有个致命窗口：删掉缓存后、DB 更新完成前，一个读请求把**旧值**重新加载进缓存，这份脏数据会长期存在。先更后删的窗口（读请求在「删后」读到旧缓存、且 DB 在「更前」）概率极低，工程上可接受。

但这仍不彻底，生产上通常加两层兜底：**延迟双删**（更新 DB + 删缓存后，延迟几百毫秒再删一次），或 **Binlog 订阅**（用 Canal 之类监听 DB 变更、异步删缓存，以 DB 为唯一事实源，MQ 保证投递）。一句话总结：缓存一致性本质是**最终一致**，追求强一致就不该引入缓存。

## 分布式锁：从 SET NX 到看门狗，再到「要不要用」

这是 Redis 所有场景里坑最深的。分四层递进。

**第一层：`SET key val NX PX 30000`。** 一条命令同时完成「不存在才设置」和「设置过期」，比 `SETNX` + `EXPIRE` 两步安全（那两步中间宕机会留下永久锁）。但它有三个经典缺陷：

1. **锁过期、业务没跑完**。30 秒到期，业务跑了 40 秒，第二个客户端进来了，互斥失效。
2. **误删别人的锁**。A 的锁过期，B 加锁成功，A 这时 `DEL` 把 B 的锁删了。必须校验「锁还是不是我的」再删，而且校验 + 删除要 Lua 原子执行。
3. **主从切换丢锁**。A 在主节点加锁成功，主节点宕机且锁还没同步到从库，新主上 B 又加锁成功——**双持锁**。这是单实例方案无法根治的。

**第二层：Redisson 的看门狗。** 解决缺陷 1（锁过期业务未完成）：默认锁过期 30 秒，一个后台任务**每 1/3 过期时间（10 秒）** 检查一次持锁状态、续期回 30 秒。锁的存储是 Hash 而非 String：

```text
lock:order:1001  →  { "clientId:threadId" : 重入次数 }
```

用 Hash 是为了**可重入**：同一线程再次加锁 `hincrby` +1，解锁 -1，减到 0 才真正 `del`。两个必须记住的坑：**一旦显式传了 `leaseTime`，看门狗就失效了**（代码评审高频问题）；`unlock()` 必须由加锁的那个线程调用，否则抛 `IllegalMonitorStateException`。看门狗选 1/3 而不是 1/2，是为了留出两次重试机会——某次续期网络抖动失败，还有下一个 10 秒窗口，三次都失败才真丢锁。

**第三层：Redlock 的争议。** 缺陷 3（主从切换丢锁）单实例和哨兵都治不了，Redlock 的做法是向 N 个（通常 5 个）完全独立的节点请求加锁，超过半数成功且总耗时小于锁过期时间才算成功。但 Martin Kleppmann 批评它依赖各节点时钟同步——进程 GC 停顿、时钟跳变会破坏锁语义，而且缺少 fencing token（持锁者 GC 停顿醒来后，可能操作已被新持锁者接管的数据）。这场争论至今没有公认结论。

**第四层：最终的判据。** Redis 锁解决的是「**多个进程不要同时干活**」（效率），不是「**数据一定不会错**」（正确性）。前者丢锁只是重复劳动，后者丢锁就是资损。判断标准一句话——**丢锁会不会导致钱算错**：会，就别只靠 Redis 锁，用 ZooKeeper/etcd 或数据库乐观锁；不会（比如防重复点击），Redisson + 幂等足够。绝大多数业务场景，单实例/哨兵 + Redisson + 业务幂等就是正确答案，Redlock 的复杂度对不上它的收益。

## 限流：三种算法，各有一个坑

**固定窗口**最简单，但有**临界突刺**——1 分钟窗口内限 100 次，第 59 秒和第 61 秒各来 100 次，中间 2 秒突刺 200 次。适合粗粒度。

**滑动窗口**（ZSet）精确，把时间轴切成连续的窗口，但**内存开销与请求量线性相关**，请求量大时 ZSet 会很大。

**令牌桶**（Lua）平滑、支持突发，是网关级首选：桶里按固定速率放令牌，请求来先取令牌，取不到就拒绝。核心逻辑用一段 Lua 原子完成「补令牌 → 扣令牌」：

```lua
-- KEYS[1] 桶key; ARGV[1] 容量; ARGV[2] 速率(个/秒); ARGV[3] 当前毫秒; ARGV[4] 请求令牌数
local capacity = tonumber(ARGV[1])
local rate = tonumber(ARGV[2])
local now = tonumber(ARGV[3])
local requested = tonumber(ARGV[4])
local lastTime = redis.call('hget', KEYS[1], 'lastTime') or now
local tokens = tonumber(redis.call('hget', KEYS[1], 'tokens') or capacity)
local delta = math.max(0, now - lastTime)
local newTokens = math.min(capacity, tokens + delta * rate / 1000)
if newTokens >= requested then
    redis.call('hset', KEYS[1], 'tokens', newTokens - requested)
    redis.call('hset', KEYS[1], 'lastTime', now)
    return 1
else
    return 0
end
```

选型上，单机内用 Guava/Sentinel，分布式小规模用 Redis，大规模网关用独立限流服务，别把 Redis 当唯一限流闸口。

## 排行榜与延迟队列：两个顺手但要知道边界的用法

**排行榜**是 Redis 最优雅的场景之一：ZSet 的跳表 O(logN) 插入，`ZRANK` 靠 span 直接算排名，`ZRANGE` 取 Top N。两个优化点：只保留 Top N（`ZREMRANGEBYRANK` 裁剪），分数相同加时间戳做次级维度。

**消息队列**则要小心边界：List 的 `LPUSH/BRPOP` 能做简易队列，但**没有 ACK，消费失败即丢**，只适合不重要的场景；要可靠，用 Stream（消费者组 + ACK + 回溯）。但 Stream 也不是专业 MQ 的替代品——它没有持久化分级存储、堆积能力受内存限制、没有事务消息和延迟消息，核心链路仍然该选 RocketMQ/Kafka。

## 收口

Redis 的高级场景，几乎每个都遵循同一条规律：**原理简单、边界清晰，坑都在「默认值」和「主从/过期」这些角落**。穿透和击穿差在「查的是不是存在的 key」，分布式锁的命门在主从切换，限流的命门在窗口边界，排行榜和队列则要看清它们的能力上限。

用好这些场景的关键，不是把它们用得更多，而是**在正确的地方用、并清楚每个场景的边界**：缓存记住「最终一致」，分布式锁记住「效率锁不是正确性锁」，限流记住「没有算法能同时精确又便宜」，队列记住「Stream 替代不了专业 MQ」。

延伸一个问题：看门狗靠一个每 10 秒跑一次的续期任务维持锁，但如果这个任务跑在 Netty 的 EventLoop 上、而你的业务代码又占满了 IO 线程，续期会被推迟、锁会意外提前释放——那么在生产上，你怎么观测「看门狗是否在正常续期」？这个答案能帮你把分布式锁从「能用」推到「可靠」。
