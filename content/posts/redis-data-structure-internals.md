在 Redis 里执行 `OBJECT ENCODING key`，你会看到一件反直觉的事：同一个逻辑类型，底层编码是**会变的**。比如一个 Hash，刚塞了几个字段时是 `listpack`，字段一多、值一长，就悄悄变成了 `hashtable`。

这不是 bug，是 Redis 快的最隐蔽一根支柱——**数据结构按场景特化**。很多人背得出「内存 + 单线程 + 多路复用」，却漏了第四样：Redis 没有用一个「通用容器」走天下，而是给每个类型准备了多套底层实现，在「省内存的小编码」和「高性能的完整结构」之间按数据形态切换。这篇就讲清这几套编码是什么、为什么切换、以及每一套背后藏着的代价。

## 一张编码切换表

先建立全局认知。Redis 的逻辑类型和底层编码是两套概念：

| 类型 | 底层编码 | 触发条件（默认） |
| :--- | :--- | :--- |
| **String** | `int` / `embstr` / `raw` | 整数 / ≤44 字节 / >44 字节 |
| **List** | `listpack` / `quicklist` | 超出阈值转 quicklist |
| **Hash** | `listpack` / `hashtable` | 字段 ≤512 且值 ≤64B / 超出 |
| **Set** | `intset` / `hashtable` | 全整数且 ≤512 / 超出 |
| **ZSet** | `listpack` / `skiplist` | ≤128 且值 ≤64B / 超出 |

一个关键背景：Redis 7.0 用 `listpack` **全面取代了 `ziplist`**（Hash/Set/ZSet 的小编码统一为 listpack）。原因是 ziplist 有一个致命的结构缺陷，第三节会讲。这套「小数据用紧凑编码、大数据用完整结构」的思路，就是 Redis 内存效率远超普通内存缓存的根本原因。

## SDS：Redis 自己的字符串

Redis 没有用 C 语言的 `char*`，而是自己造了个 `SDS`（Simple Dynamic String）。原因有三，都直击 C 字符串的痛点：

```c
struct __attribute__ ((__packed__)) sdshdr8 {
    uint8_t len;    // 已用长度
    uint8_t alloc;  // 分配总长度
    unsigned char flags; // 低3位存类型
    char buf[];     // 柔性数组
};
```

**第一，二进制安全。** C 字符串以 `\0` 判断结尾，所以存不了图片、序列化字节流这类内容（中间一出现 `\0` 就被截断）。SDS 用 `len` 记录长度，内容里随便是什么字节都行。

**第二，O(1) 取长度。** C 字符串的 `strlen` 要遍历到 `\0`，是 O(N)；SDS 直接读 `len` 字段，O(1)。别小看这一点——`STRLEN` 命令和很多内部判断都依赖它。

**第三，预分配 + 惰性释放。** 扩容时多分配空间（小于 1MB 翻倍、超过 1MB 每次加 1MB），缩短时不立刻归还内存，减少 `realloc` 的次数和内存抖动。

SDS 还有 5 种变体：`sdshdr5/8/16/32/64`，按字符串长度选择元数据最小的那一种，极致省内存。这里藏着一个很值得记的推导——**为什么 embstr 的门槛是 44 字节**：

```text
jemalloc 64B 内存块 = redisObject(16B) + sdshdr8 头(3B) + buf(44B) + '\0'(1B)
  → 16 + 3 + 44 + 1 = 64，正好一个内存块，零碎片
  → 超过 44B 就落不进 64B 块，转 raw（两次分配：robj + SDS）
```

一句话理解这个门槛：Redis 让 ≤44 字节的短字符串连同对象头一起塞进一个 64 字节的内存块里，一次分配、零碎片、还正好卡在 CPU 缓存行上。超过就拆成两次分配。所以「短字符串用 embstr」本质是一个内存布局的优化，不是语法差异。

## listpack：从结构上消灭连锁更新

这是 Redis 7.0 最值得知道的一个改动。要理解 listpack 为什么好，先看 ziplist 的缺陷在哪。

ziplist 的每个节点是 `<prevlen> <encoding> <entry-data>`，其中 `prevlen` 记录**前一个节点的长度**。问题来了：当你往中间插入一个节点、导致某个节点的长度跨过阈值（比如从 254 字节变成 255 字节），它后面的节点就要跟着扩容自己的 `prevlen` 字段，而 `prevlen` 字段的扩容又可能让**再后面**的节点跟着变——这就是「连锁更新」，最坏 O(N²)。

listpack 的解法很巧妙：节点改成 `<encoding> <content> <backlen>`，只记录**自己的**长度，彻底删掉了对前一个节点的依赖。于是「前节点变大导致后续级联更新」这件事，在结构上就不可能发生了。这也是为什么 7.0 敢把 Hash/Set/ZSet 的小编码全部换成 listpack。

而 `quicklist` 是另一层设计：它是一个双向链表，每个节点里再装一个 listpack（7.0 前是 ziplist）。节点内连续内存、节点间用链表串——既拿到连续内存的省内存和缓存友好，又避免整条链被一次连锁更新打穿。`fill` 控制每个节点的容量，`compress` 控制中间节点是否 LZF 压缩。

## dict 的渐进式 rehash：为什么不敢一次搬完

Hash 底层的 hashtable 是 `dict`，它最精华的设计是**渐进式 rehash**。先看结构：

```c
typedef struct dict {
    dictType *type;
    void *privdata;
    dictht ht[2];       // 两个哈希表
    long rehashidx;     // -1 表示未在 rehash
} dict;
```

哈希表要扩容时，正常的做法是把旧表里的所有 key 一次性搬进新表。但对 Redis 来说这是灾难——一张表可能有百万 key，一次性搬完主线程要卡住几百毫秒甚至更久，而这期间**所有命令都被阻塞**。别忘了上一篇讲过的核心约束：单条慢操作会阻塞所有人。

所以 Redis 把「一次大搬迁」拆成「无数次小搬迁」：`ht[0]` 是旧表、`ht[1]` 是新表，每次增删改查时**顺带迁移一个桶**，再由 `serverCron` 每 100ms 定时批量迁移一部分。这样迁移被摊到无数个命令的间隙里，任何单条命令的延迟都不会被显著拖慢。

rehash 期间的一致性怎么保证？规则很简洁：**读查两表、写只进 ht[1]**。触发条件是负载因子 ≥1 时扩容（但 BGSAVE 期间阈值提高到 ≥5，因为 fork 出的子进程靠 COW 共享内存，这时扩容会制造更多写、更费内存），≤0.1 时缩容。

一个容易漏的细节：渐进式 rehash 期间，`ht[0]` 和 `ht[1]` 同时存在，内存占用接近峰值，所以**rehash 是 Redis 内存瞬时膨胀的一个隐蔽来源**——监控里看到内存突然多了一截、又慢慢回落，常常就是它。

## skiplist：为什么 ZSet 用跳表不用红黑树

有序集合（ZSet）的完整编码是「跳表 + 哈希表」双结构。哈希表负责 `ZSCORE` 的 O(1) 点查，跳表负责排序和范围查询。问题来了：排序这事，红黑树不是标准答案吗，为什么 Redis 偏要用跳表？

跳表本质上是一个「带多层索引的链表」：每个节点随机决定层数（每层晋升概率 25%），高层索引让查找可以「跳着走」，平均 O(logN)。它的节点长这样：

```c
typedef struct zskiplistNode {
    sds ele;
    double score;
    struct zskiplistNode *backward;
    struct zskiplistLevel {
        struct zskiplistNode *forward;
        unsigned long span;   // 跨度
    } level[];
} zskiplistNode;
```

用跳表而不是红黑树，有三个很实际的理由：

1. **范围查询天然高效**。跳表按层顺序遍历，`ZRANGE` 这种「取一段连续区间」的操作直接就是线性的；红黑树要做中序遍历，还得维护栈，更绕。
2. **实现和调试简单**。跳表没有旋转、染色那套平衡操作，代码量小得多。
3. **`span` 支持按排名定位**。注意节点里的 `span` 字段——`ZRANK` 要回答「这个元素排第几」，跳表累加跨过的 span 就行；红黑树要支持这个，得额外维护子树大小，实现复杂得多。

代价也是有的：跳表靠随机层数，理论上存在「层数运气差」的退化（虽然概率极低），而且比红黑树多占一些指针内存。但 Redis 要的核心是「范围查询 + 排名」这两件事，跳表是明显更合适的那个。

## 收口

回头看，Redis 的「快」从来不是某一个单一魔法，而是四个层次的协同：内存解决 IO、单线程解决锁、多路复用解决连接，而**数据结构特化解决「每种数据形态都有最省的存法」**。SDS 让短字符串塞进一个缓存行，listpack 让紧凑编码不再有连锁更新，渐进式 rehash 让扩容不阻塞，跳表让范围查询和排名都便宜。

但每一套特化都不是免费的：embstr 超 44 字节就退化、listpack 超过阈值就切换完整结构、rehash 期间内存瞬时膨胀、跳表多占指针内存。理解这些代价，你才能读懂 `OBJECT ENCODING` 的输出，也才能在内存告急时知道该往哪看。

延伸一个问题：一个 Set 在「全整数且 ≤512 个」时用 intset、一旦混入一个字符串就整体升级成 hashtable，而且**升级后不再降级**。如果这个字符串后来被删掉了，Set 的内存为什么不会自动回落？这能帮你理解 Redis 内存「只涨不跌」的另一个来源。
